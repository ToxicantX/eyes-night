# OpenClaw 晚间复盘（2026-03-09）

本期聚焦“Skills + 工作流 + 稳定性”可落地经验，官方动态仅做一条压缩汇总。

## 1) 健康巡检从“偶发执行”升级为“风险分层清单”（Skills: healthcheck）
- **变化/学习**：把安全检查从“想到才跑”改成固定清单（SSH、更新策略、暴露面、日志），并按风险容忍度做分层。
- **具体步骤**：
  1. 先定义高/中/低风险项（如 SSH root 登录、密码认证、开放端口、自动更新策略）。
  2. 用 healthcheck 形成标准检查顺序；先“读配置”，后“改配置”。
  3. 把“立即修复项”与“观察项”分开，避免一次改太多引入新故障。
- **可衡量影响**：
  - 新机器首轮加固可从“>2 小时摸索”降到“30-50 分钟标准化执行”。
  - 高风险误配置（如过宽 SSH 策略）可在首轮即发现。
- **坑点**：一次性收紧防火墙/SSH 容易把自己锁在门外；先保留回滚通道。
- **建议**：**Act now**（立刻执行）。
- **来源**：
  - 主链接：<https://github.com/wushengxi/openclaw>
  - 备份：<https://man7.org/linux/man-pages/man5/sshd_config.5.html>

## 2) tmux 远程控制模式：把“交互自动化”从脆弱脚本变为可恢复流程
- **变化/学习**：tmux 技能核心价值不是“发按键”，而是“可恢复”：断线后还能接续会话与上下文。
- **具体步骤**：
  1. 所有长任务统一进 tmux session（命名含日期/任务名）。
  2. 关键步骤前后都抓 pane 输出（用于审计与回放）。
  3. 失败时优先“回放最近屏幕 + 重放最小按键序列”，而非整段重跑。
- **可衡量影响**：
  - 交互链路中断后的恢复时间可下降到分钟级。
  - CLI 自动化“半程失败全盘重来”的概率显著下降。
- **坑点**：未做 pane 输出留档，失败后无法定位哪一步偏移。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://github.com/tmux/tmux/wiki>
  - 备份：<https://man7.org/linux/man-pages/man1/tmux.1.html>

## 3) 天气类能力（weather skill）最稳方案：双源校验 + 降级输出
- **变化/学习**：wttr.in 快速、Open‑Meteo 结构化强；组合后既有可读性又可程序化。
- **具体步骤**：
  1. 默认先取 wttr.in 文本快照用于人类阅读。
  2. 同时拉 Open‑Meteo 核心字段（温度、降水概率、风速）用于阈值判断。
  3. 任一源超时即降级到另一源，保证“有结果优先”。
- **可衡量影响**：
  - 单源故障导致的“空响应”可显著降低。
  - 对提醒场景（出门、通勤）可稳定输出“是否带伞/加衣”决策。
- **坑点**：不同源时区与小时粒度不一致，直接对比会误判。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://wttr.in/:help>
  - 备份：<https://open-meteo.com/en/docs>

## 4) skill-creator 实践：先把“边界”写进技能，再写步骤
- **变化/学习**：高质量技能不只写“怎么做”，更要写“什么时候不用它”。
- **具体步骤**：
  1. 在技能描述里先写适用/不适用范围。
  2. 把外部 API 写操作做“批量化、串行化、限速化”。
  3. 每个技能都补“失败回退路径”（重试上限、降级策略、人工接管点）。
- **可衡量影响**：
  - 误触发错误技能的概率下降。
  - 外部 API 429 问题更可控，失败重跑成本降低。
- **坑点**：只写 happy path，实际一遇到限流就雪崩。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://platform.openai.com/docs/guides/rate-limits>
  - 备份：<https://www.rfc-editor.org/rfc/rfc6585>

## 5) Browser Relay 运营侧经验：优先“少轮次高信息密度”而非高频点击
- **变化/学习**：浏览器自动化最耗的是往返轮次，不是单次动作；减少循环比“优化单步”收益更大。
- **具体步骤**：
  1. 页面抓取时尽量一次拿全关键区块（标题、主文、分页状态）。
  2. 写入类动作合并提交，避免一条一条发。
  3. 对动态页面设置“可观察完成条件”（元素出现/网络静默）再进入下一步。
- **可衡量影响**：
  - 端到端执行时间通常可下降 20%+（取决于页面复杂度）。
  - “元素未就绪导致误操作”显著减少。
- **坑点**：用固定 sleep 代替状态判断，抖动环境下极不稳定。
- **建议**：**Watch**（优先改高频流程）。
- **来源**：
  - 主链接：<https://playwright.dev/docs/actionability>
  - 备份：<https://developer.chrome.com/docs/devtools/>

## 6) cron + heartbeat 设计：用 heartbeat 做批处理，用 cron 做精确定时
- **变化/学习**：二者不是互斥关系；最佳实践是“能批就批，必须准点才上 cron”。
- **具体步骤**：
  1. heartbeat 负责低时效检查（邮箱、日历、提醒聚合）。
  2. cron 负责硬时点任务（固定时间发布、提醒、备份）。
  3. 维护最小状态文件（最近检查时间、最后通知时间）避免重复打扰。
- **可衡量影响**：
  - API 调用量下降，通知噪音下降。
  - 准点任务误差可控，日常巡检更省成本。
- **坑点**：把所有任务都塞 cron，后期维护成本陡增。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://en.wikipedia.org/wiki/Cron>
  - 备份：<https://github.com/wushengxi/openclaw>

## 7) 社区案例：子代理编排从“轮询”转向“事件驱动通知”
- **变化/学习**：实践里更推荐“启动后等待完成推送”，仅在介入/排障时查状态，避免列表轮询。
- **具体步骤**：
  1. 复杂任务先拆子代理并明确交付物路径。
  2. 主会话只在需要介入时查询一次状态。
  3. 子任务完成后回传摘要 + 产物文件，主流程再统一整合。
- **可衡量影响**：
  - 主流程 token/调用消耗下降。
  - 并发任务时的人为干预频率减少。
- **坑点**：高频查询状态列表，既耗资源又干扰任务本身。
- **建议**：**Watch**（在多任务日优先采用）。
- **来源**：
  - 主链接：<https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview>
  - 备份：<https://github.com/microsoft/autogen>
