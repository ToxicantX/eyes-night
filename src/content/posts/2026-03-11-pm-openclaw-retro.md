## 1) healthcheck：把“安全检查”从一次性动作改成可持续基线（Skills 实践）

**发生了什么 / 学到什么**  
把主机安全硬化从“临时巡检”改成“有节奏的基线复查”更有效：先定风险容忍度，再做最小必要加固（SSH、更新策略、暴露面、日志）。

**可执行步骤**
1. 先定义风险档位（个人开发机 / 团队节点 / 暴露公网节点）。
2. 固化检查项：SSH 配置、补丁策略、开放端口、最小权限。
3. 将检查结果结构化记录（同一模板，便于日对比）。
4. 对高风险项设置 cron 周期复查，低风险项改周报汇总。

**可量化影响**
- 漏项回归率可从“随机”降到“按周期可追踪”。
- 平均排查时间（MTTR）可因模板化缩短（常见可缩短 20%+）。

**坑点**
- 只做“高分扫描”不做资产上下文，误报会拖垮执行。
- 一次性全量加固容易影响开发效率。

**建议**：**现在就做（Act now）**

**来源（原始链接）**
- Primary: https://www.cisecurity.org/benchmark  
- Backup: https://github.com/CISOfy/lynis

## 2) tmux：把交互式 CLI 变成可复盘流水线（Skills 实践）

**发生了什么 / 学到什么**  
tmux 适合托管长任务、交互命令和断线恢复；关键不是“会用”，而是“统一会话命名 + pane 抓取 + 失败重放”。

**可执行步骤**
1. 统一命名规范：`proj-env-role`（如 `oc-prod-publisher`）。
2. 长任务放独立 pane，日志落盘（stdout/stderr 分离）。
3. 关键步骤前后打时间戳，失败后可定位到命令粒度。
4. 用脚本封装 attach/capture，减少手工操作。

**可量化影响**
- 断线后恢复效率显著提升（无需重跑全链路）。
- 问题复盘可定位到分钟级窗口。

**坑点**
- pane 输出不落盘，事后无法追责。
- 单会话塞太多任务导致上下文污染。

**建议**：**现在就做（Act now）**

**来源（原始链接）**
- Primary: https://github.com/tmux/tmux/wiki  
- Backup: https://man7.org/linux/man-pages/man1/tmux.1.html

## 3) weather：天气数据接入运营日程的“轻自动化”打法（Skills 实践）

**发生了什么 / 学到什么**  
天气信息不只是展示，可直接参与运营排期（出行、线下拍摄、设备搬运窗口）。Open-Meteo/wttr 这类免 Key 源适合做低成本信号输入。

**可执行步骤**
1. 约定固定城市与时间窗（早/晚两次）。
2. 只抽取决策字段：降雨概率、体感温度、风速。
3. 触发阈值告警（例如降雨概率 >60% 即变更外出计划）。
4. 与日程任务绑定：自动附“天气风险注释”。

**可量化影响**
- 临时改期次数下降。 
- 外勤准备遗漏率下降（雨具/设备防护）。

**坑点**
- 多源数据口径不一致，需统一一个主源。
- 没有阈值会导致“看了等于没看”。

**建议**：**观察并扩展（Watch）**

**来源（原始链接）**
- Primary: https://open-meteo.com/en/docs  
- Backup: https://wttr.in/:help

## 4) skill-creator：技能文档先“约束后扩展”（Skills 实践）

**发生了什么 / 学到什么**  
技能质量的核心不是篇幅，而是触发条件、边界、失败处理和输出模板。先把“何时不用”写清，误触发率会明显下降。

**可执行步骤**
1. 每个 Skill 增加“适用/不适用”清单。 
2. 固化输入参数校验与失败回退策略。 
3. 输出模板统一为“结论 + 证据 + 下一步”。 
4. 每周审计一次过时引用和无效步骤。

**可量化影响**
- 技能误调用率可下降。 
- 交接成本下降（新成员更快上手）。

**坑点**
- 把 Skill 写成“万能说明书”，导致执行不稳定。
- 忽略版本漂移（CLI 参数变更后文档失效）。

**建议**：**现在就做（Act now）**

## 5) cron + heartbeat：提醒系统从“定时触发”升级为“可达性设计”（Skills 实践）

**发生了什么 / 学到什么**  
仅有 cron 还不够，关键是 heartbeat/wake 机制：任务到点 ≠ 用户可见。应把“触发时间、投递方式、失败重试”作为一个整体设计。

**可执行步骤**
1. 区分 `at/every/cron` 三类任务，避免滥用。 
2. 对关键提醒启用 announce 或 webhook 兜底。 
3. 为每个任务记录 run 历史（成功率、延迟、失败原因）。 
4. 对高价值提醒增加“次级补发窗口”。

**可量化影响**
- 漏提醒率下降。 
- 关键任务到达率提升（可按周统计）。

**坑点**
- 只关注“是否执行”，忽略“是否送达”。
- 间隔任务无锚点，漂移后影响节律。

**建议**：**现在就做（Act now）**

- Primary: https://en.wikipedia.org/wiki/Cron

## 6) Sub-agent 编排：复杂任务先拆“独立会话责任单元”（Skills 实践）

**发生了什么 / 学到什么**  
复杂任务（抓取→整理→发布）在单线程会话里容易上下文拥堵。拆分成 sub-agent（采集、校验、发布）后，主会话只做编排与验收更稳。

**可执行步骤**
1. 按职责拆 2-3 个子会话（避免过细）。
2. 每个子会话定义输入/输出契约（文件、字段、截止时间）。
3. 主会话只做状态检查、冲突协调和最终合并。
4. 失败子会话可单独重跑，不影响全局。

**可量化影响**
- 长任务可中断恢复，重跑成本下降。 
- 并行执行时总耗时可缩短。

**坑点**
- 未定义契约会导致“并行混乱”。
- 过度拆分反而增加通信开销。

**建议**：**现在就做（Act now）**

**来源（原始链接）**
- Primary: https://docs.langchain.com/docs/use-cases/multi-agent  
- Backup: https://www.anthropic.com/engineering/building-effective-agents

## 7) 社区案例：Browser Relay / Playwright 运维实践趋向“可回放证据链”（社区）

**发生了什么 / 学到什么**  
社区近期实践强调：浏览器自动化不仅要跑通，还要保留 trace/screenshot/network 证据链，用于失败定位与审计。

**可执行步骤**
1. 默认开启 trace（关键流程）。
2. 每个失败步骤自动截图并保存 HAR/网络日志。
3. 把“选择器稳定性”作为首要质量指标（减少脆断）。
4. 失败样本沉淀成回归用例。

**可量化影响**
- 自动化失败定位时间显著降低。 
- 脆弱用例可持续收敛。

**坑点**
- 不做证据留存导致“复现靠运气”。
- 过度依赖文本选择器，页面改版即雪崩。

**建议**：**观察并跟进（Watch）**

## 8) 官方更新（仅 1 条）：自动化能力持续向“代理化工作流”推进（官方）

**发生了什么 / 学到什么**  
官方生态的共同方向是：把“聊天问答”推进到“可调用工具 + 可编排流程 + 可观测结果”的代理化能力。

**可执行步骤**
1. 将一次性脚本改为可重复工作流。 
2. 引入工具调用前后状态记录（输入、输出、耗时）。

**坑点**
- 只追新功能，不建设可观测和回滚。
- 自动化无分级，导致高风险任务缺少人工闸门。
