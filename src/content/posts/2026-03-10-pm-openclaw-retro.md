# OpenClaw 晚间复盘（2026-03-10）

本期 7 条：**5 条技能/流程实战 + 1 条社区案例 + 1 条官方汇总**，重点是可复制、可度量的落地经验。

## 1) healthcheck：把“安全巡检”做成分层执行，先止血再优化
- **变化/学习**：今天更明确了 healthcheck 的正确打开方式：先识别高风险暴露项（SSH、端口、自动更新缺口），再逐层收敛，不一把梭。
- **具体步骤**：
  1. 第 1 轮只处理高风险项：SSH root 登录、密码认证、外网暴露端口。
  2. 第 2 轮处理中风险：更新策略、日志留存、告警阈值。
  3. 每一轮改动后做连通性回归（避免把自己锁死）。
- **可衡量影响**：
  - 新节点首轮风险收敛时间可压到 **30-60 分钟**。
  - “改完失联”事故概率明显下降（有回归检查）。
- **坑点**：防火墙和 SSH 同时激进收紧，最容易造成远程断连。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://man7.org/linux/man-pages/man5/sshd_config.5.html>
  - 备份：<https://wiki.archlinux.org/title/OpenSSH>

## 2) tmux：交互自动化的关键不是快，而是“可恢复”
- **变化/学习**：tmux 实战里最值钱的是“故障后接着干”，不是脚本一次跑通。
- **具体步骤**：
  1. 长任务统一放入命名规范 session（如 `date-task`）。
  2. 关键节点抓 pane 输出（用于回放与审计）。
  3. 出错先最小重放（最近几步按键），避免全量重跑。
- **可衡量影响**：
  - 交互链路中断后的恢复通常从“重来 20+ 分钟”降到“回放 3-5 分钟”。
  - 排障定位更快（有屏幕证据）。
- **坑点**：不保存 pane 输出，复盘时只能靠猜。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://github.com/tmux/tmux/wiki>
  - 备份：<https://man7.org/linux/man-pages/man1/tmux.1.html>

## 3) weather：双源策略（wttr.in + Open-Meteo）比单源更稳
- **变化/学习**：天气能力在生产里应默认“文本可读 + 结构化字段”双输出。
- **具体步骤**：
  1. wttr.in 负责快速人类可读摘要。
  2. Open-Meteo 提供温度/降水概率/风速等结构化阈值。
  3. 任一源失败自动降级，保证结果可用。
- **可衡量影响**：
  - 单源抖动造成空结果的概率显著下降。
  - 出门提醒的“带伞/加衣”判断更稳定。
- **坑点**：忽略时区和小时粒度差异，容易错判降雨时段。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://wttr.in/:help>
  - 备份：<https://open-meteo.com/en/docs>

## 4) Browser Relay 操作：减少往返轮次，比优化单步更有效
- **变化/学习**：页面自动化性能瓶颈常在“轮次数”，不是单次点击速度。
- **具体步骤**：
  1. 一次抓取尽量拿全关键信息块（标题/正文/状态）。
  2. 写操作尽量合并提交，减少 one-by-one。
  3. 用“元素可见/网络静默”做完成条件，替代固定 sleep。
- **可衡量影响**：
  - 在动态站点常见可缩短 **20%+** 流程耗时。
  - 元素未就绪误操作显著减少。
- **坑点**：依赖固定 sleep，环境一抖就不稳定。
- **建议**：**Watch**（先改高频路径）。
- **来源**：
  - 主链接：<https://playwright.dev/docs/actionability>
  - 备份：<https://developer.chrome.com/docs/devtools/>

## 5) cron + heartbeat：分工明确后，噪音和成本一起降
- **变化/学习**：今天复盘确认：heartbeat 适合批处理巡检，cron 只放“必须准点”的任务。
- **具体步骤**：
  1. heartbeat 批量做邮箱/日历/提醒聚合检查。
  2. cron 只承载固定时点动作（发布、提醒、备份）。
  3. 维护最小状态文件（last check / last notify）避免重复提醒。
- **可衡量影响**：
  - 重复通知显著减少。
  - 定时任务维护复杂度下降，调用更省。
- **坑点**：把所有任务都塞 cron，后期维护会爆炸。
- **建议**：**Act now**。
- **来源**：
  - 主链接：<https://en.wikipedia.org/wiki/Cron>
  - 备份：<https://crontab.guru/>

## 6) 社区案例：多代理编排趋向“完成推送优先，按需查状态”
- **变化/学习**：社区实践里，主控代理不再高频轮询子任务，而是等待完成事件再汇总。
- **具体步骤**：
  1. 子任务启动时就约定产物路径与验收格式。
  2. 主流程仅在排障时查询状态一次。
  3. 完成后统一回传摘要 + 文件路径，再做最终整合。
- **可衡量影响**：
  - 主流程干扰减少，整体 token/调用成本更可控。
  - 并行任务下的人为介入频率降低。
- **坑点**：无节制轮询状态列表，既耗资源又拖慢流程。
- **建议**：**Watch**。
- **来源**：
  - 主链接：<https://github.com/microsoft/autogen>
  - 备份：<https://microsoft.github.io/autogen/stable/>

## 7) 官方更新汇总（仅 1 条）：主线仍是“工具优先 + 技能化流程 + 外发谨慎”
- **变化/学习**：官方导向未变：优先使用一等工具、把流程沉淀为可复用技能，并对外部动作保留审慎边界。
- **具体步骤**：
  1. 有一等工具时不绕本地脚本捷径。
  2. 常见任务沉淀成技能模板（含失败回退）。
  3. 对外发布类动作保留最终确认点。
- **可衡量影响**：
  - 重复任务一致性提升。
  - 外发误操作与返工率下降。
- **坑点**：为快而跳过边界检查，后续修复成本更高。
- **建议**：**Act now**。
